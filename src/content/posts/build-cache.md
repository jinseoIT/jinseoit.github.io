# 정적 사이트 배포, 왜 수정 사항이 반영되지 않을까

> "방금 배포했는데 왜 안 바뀌어요?"
> "강력 새로고침(Ctrl+Shift+R)을 해야 겨우 새 버전이 뜨는데요?"

정적 사이트를 운영해본 사람이라면 한 번쯤 들어봤을 말이다. 빌드도 잘 됐고, S3나 Vercel에 잘 올라갔고, 직접 들어가 봐도 새 버전이 보이는데 — 사용자에게는 여전히 옛날 화면이 떠 있다. 원인은 거의 항상 하나, **캐싱**이다.

이 글은 "왜 반영이 안 되는지"를 짚고, "이렇게 하면 안 되고 이렇게 해야 한다"를 정리한다. 이론 설명보다는 실제 배포 환경에서 무엇이 잘못되었고 어떻게 고쳐야 하는지에 초점을 둔다.

---

## 출발점: 왜 변경이 즉시 반영되지 않을까

브라우저는 한 번 받은 자산을 가급적 다시 받지 않으려 한다. 이게 캐싱의 본질이고 좋은 일이다 — 매번 같은 JS 파일을 다운로드한다면 사이트는 느려질 것이다.

문제는 **"새 버전이 나왔는데 브라우저가 그걸 모를 때"** 발생한다. 캐시 헤더를 잘못 설정했거나 아예 설정하지 않으면, 브라우저(또는 CDN)는 자기가 가진 옛 버전이 여전히 유효하다고 믿어버린다.

이 문제를 푸는 핵심 아이디어는 단순하다.

> **"바뀌는 것"과 "안 바뀌는 것"을 다르게 캐시한다.**

같은 캐시 정책을 모든 파일에 들이미는 순간 문제가 시작된다.

---

## 1. 자산 타입별 차별 캐싱

### ❌ 이렇게 하면 안 된다

모든 파일에 동일한 캐시 정책을 적용하는 경우. 가장 흔한 두 가지 실수가 있다.

**(1) 캐시 헤더를 아예 설정하지 않기**

서버나 호스팅의 기본값에 맡겨두면 브라우저마다 휴리스틱이 달라 예측이 어렵다. 어떤 파일은 1시간, 어떤 파일은 며칠 동안 캐시될 수 있다. "왜 어떤 사용자만 옛 버전을 보지?"의 전형적 시나리오.

**(2) 모든 파일에 길게 캐시 적용**

```
Cache-Control: public, max-age=31536000
```

`index.html`까지 1년 캐시해버리면, 사용자의 브라우저가 1년간 새 버전을 볼 일이 없다. 강력 새로고침을 해야만 갱신된다.

### ✅ 이렇게 해야 한다

자산을 두 그룹으로 나누는 것이 출발점이다.

**불변 자산 (immutable assets)** — 파일명에 해시가 들어간 JS, CSS, 이미지, 폰트 등. 내용이 바뀌면 파일명 자체가 바뀌므로 매우 길게 캐시해도 안전하다.

```
Cache-Control: public, max-age=31536000, immutable
```

**가변 자산 (mutable assets)** — `index.html`처럼 파일명이 고정된 진입점. 짧게 캐시하거나 매 요청마다 검증해야 새 배포가 빠르게 반영된다.

```
Cache-Control: no-cache
# 또는
Cache-Control: public, max-age=0, must-revalidate
```

> **자주 헷갈리는 부분**: `no-cache`는 "캐시하지 말라"가 아니다. "캐시는 해두되, 쓰기 전에 서버에 검증하라"는 뜻이다. 진짜 캐시를 막고 싶으면 `no-store`를 써야 한다. 정적 사이트의 HTML에는 거의 항상 `no-cache`가 정답이다.

---

## 2. 파일명 해싱 (Cache Busting)

위 전략의 핵심 전제다. "불변 자산"을 1년 캐시해도 안전한 이유는 내용이 바뀌면 파일명도 바뀌기 때문이다.

### ❌ 이렇게 하면 안 된다

```html
<script src="/js/app.js"></script>
<link rel="stylesheet" href="/css/style.css" />
```

파일명이 고정되어 있으면 새 버전을 배포해도 브라우저는 "어, 나 이거 캐시에 있는데?" 하고 옛 파일을 그대로 쓴다. 캐시를 길게 잡았다면 며칠씩 옛 버전이 유지된다.

### ✅ 이렇게 해야 한다

빌드 도구의 콘텐츠 해싱을 활성화한다. Vite, webpack, Next.js, esbuild 같은 번들러는 빌드 시 파일 내용의 해시를 자동으로 파일명에 붙여준다.

```html
<script src="/js/app.a3f2c1.js"></script>
<link rel="stylesheet" href="/css/style.7b9e44.css" />
```

내용이 바뀌면 URL이 바뀌므로 브라우저는 "이건 처음 보는 파일이네" 하고 새로 받아온다. 옛 파일이 캐시에 남아 있어도 아무도 요청하지 않으니 무해하다.

HTML에서만 해시 없는 이름으로 자산을 참조하기 때문에, **"HTML은 짧게, 자산은 길게"** 캐시하는 것만으로 정합성이 자연스럽게 유지된다. HTML이 갱신되는 순간 거기에 박힌 새 자산 URL을 따라가게 된다.

---

## 3. ETag / Last-Modified로 검증

### ❌ 이렇게 하면 안 된다

가변 자산(HTML)을 캐시는 하지 않으면서 매번 본문 전체를 풀로드한다. 작은 사이트는 모르겠지만, HTML이 커지거나 트래픽이 많아지면 낭비가 커진다.

### ✅ 이렇게 해야 한다

`ETag`나 `Last-Modified` 헤더로 검증을 활용한다. 브라우저는 이전에 받은 ETag를 `If-None-Match`로 보내고, 변경이 없으면 서버는 본문 없이 `304 Not Modified`만 응답한다.

```
HTTP/1.1 304 Not Modified
ETag: "a3f2c1"
```

대부분의 정적 호스팅(Netlify, Vercel, S3+CloudFront, Cloudflare Pages)은 자동으로 처리해주므로 직접 신경 쓸 일은 적다. 다만 직접 Nginx/Apache로 운영한다면 기본 설정을 한 번 확인해두는 게 좋다 — 의외로 ETag가 비활성화된 환경도 있다.

---

## 4. CDN 엣지 캐싱

### ❌ 이렇게 하면 안 된다

CDN을 두고도 배포 후 캐시 무효화(purge)를 하지 않는다. 브라우저 캐시 헤더만 신경 쓰고 CDN 엣지에는 옛 HTML이 살아 있는 상황. 사용자가 새로고침해도 CDN이 옛 HTML을 돌려주니 새 자산 URL을 알 길이 없다.

### ✅ 이렇게 해야 한다

`s-maxage`로 CDN 전용 TTL을 따로 줄 수 있다. 브라우저보다 CDN에 더 오래 캐시해두면 origin 부하를 크게 줄일 수 있다.

```
Cache-Control: public, max-age=0, s-maxage=86400, stale-while-revalidate=604800
```

`stale-while-revalidate`는 만료된 캐시를 즉시 응답하면서 백그라운드로 갱신하는 패턴이다. 사용자가 느끼는 지연 없이 신선도를 유지할 수 있어 정적 사이트와 궁합이 좋다.

그리고 **배포 시 CDN purge를 자동화하자**. 보통 CI/CD 파이프라인의 마지막 단계에 넣는다.

```bash
# 예: CloudFront
aws cloudfront create-invalidation \
  --distribution-id ABCDEFG \
  --paths "/index.html" "/"
```

`/*`로 전체를 무효화할 필요는 없다. **HTML만 무효화하면 충분한 경우가 많다** — 자산은 어차피 해시 때문에 새 URL이라 옛 캐시는 자연 도태된다. 전체 purge는 비용도 들고 캐시 효율도 떨어뜨린다.

---

## 5. Service Worker — 가장 위험한 함정

오프라인 지원이나 더 세밀한 캐시 제어가 필요하면 Service Worker를 쓴다. 하지만 가장 무서운 캐싱 버그가 여기서 나온다.

### ❌ 이렇게 하면 안 된다

**Service Worker를 등록만 해놓고 라이프사이클 관리를 안 하기.** Service Worker는 한번 등록되면 사용자 브라우저에 "거주"한다. 배포를 새로 해도 옛 Service Worker가 살아남아 옛 자산을 계속 서빙할 수 있다. 최악의 경우 사용자가 사이트를 며칠, 몇 주씩 옛 버전으로 보게 된다.

또 흔한 실수:

- HTML까지 Cache First로 캐시 → 배포해도 영원히 안 바뀜
- 캐시 버전 관리 없이 운영 → 옛 캐시가 무한 누적
- Service Worker 자체 업데이트 전략 부재 → unregister 못 하면 손쓸 방법이 없음

### ✅ 이렇게 해야 한다

먼저 **정말 필요한지부터 따져본다.** 단순 정적 사이트라면 Service Worker 없이 캐시 헤더만 잘 잡아도 충분하다.

써야 한다면 자산별 전략을 분리한다.

- **Cache First** — 폰트, 아이콘 등 거의 안 바뀌는 자산
- **Network First** — 최신성이 중요한 HTML, API 응답
- **Stale While Revalidate** — 약간 오래된 데이터도 괜찮은 이미지, API
  [Workbox](https://developer.chrome.com/docs/workbox) 같은 라이브러리를 쓰면 이 패턴들을 선언적으로 적용할 수 있고, 캐시 버전 관리와 옛 캐시 정리도 알아서 해준다. 직접 짜다 보면 거의 확실히 한 번은 망가진다.

마지막으로 **비상 탈출구를 만들어두자.** Service Worker가 자기 자신을 unregister할 수 있는 경로를 코드에 남겨둔다. 진짜로 큰일 났을 때 새 버전을 푸시해서 모든 사용자의 SW를 정리할 수 있어야 한다.

## 6. preload 방법

직접적인 캐싱은 아니지만 함께 쓰면 좋은 것들이다.

```html
<!-- 곧 필요한 자산을 우선 로드 -->
<link rel="preload" href="/fonts/main.woff2" as="font" crossorigin />

<!-- 다음 페이지에서 쓸 자산을 유휴 시간에 미리 로드 -->
<link rel="prefetch" href="/js/next-page.a3f2c1.js" />

<!-- 외부 도메인에 미리 TCP/TLS 연결 -->
<link rel="preconnect" href="https://api.example.com" />
```

캐싱으로 "두 번째 방문"을 빠르게 만든다면, 이 방법들은 "첫 방문"의 체감 속도를 끌어올린다.

## 정리: 실무 권장 조합

대부분의 정적 사이트라면 이 정도면 충분하다.

| 자산 유형             | Cache-Control                                                              |
| --------------------- | -------------------------------------------------------------------------- |
| HTML (`index.html`)   | `no-cache` 또는 `max-age=0, s-maxage=86400, stale-while-revalidate=604800` |
| 해시된 JS/CSS         | `public, max-age=31536000, immutable`                                      |
| 해시된 이미지/폰트    | `public, max-age=31536000, immutable`                                      |
| 해시 없는 이미지/폰트 | `public, max-age=604800` (1주, 보수적으로)                                 |

배포 파이프라인 체크리스트:

- 빌드 도구의 콘텐츠 해싱 활성화 — Vite/webpack/Next.js는 기본 활성화
- 호스팅에서 자산 타입별로 다른 캐시 헤더 설정
- CDN 사용 중이라면 배포 후 HTML purge 자동화
- Service Worker는 정말 필요할 때만, 그리고 라이프사이클 관리 철저히
- 배포 직후 시크릿 모드로 한 번 확인

## 마치며

캐싱은 "동작하지 않을 때"는 아주 답답하지만, "잘 동작할 때"는 보이지 않는다. 정적 사이트의 캐싱 전략은 결국 **무엇이 변하고 무엇이 변하지 않는지**를 빌드 도구·HTTP 헤더·CDN·브라우저에 정확히 알려주는 일이다.

해시 붙은 자산은 1년 캐시, HTML은 매번 검증, CDN은 배포 시 purge — 이 세 가지만 지켜도 "왜 안 바뀌죠?" 같은 문의는 거의 사라진다.
